# Banco de Dados — PQF

Banco Postgres via Supabase, com Row Level Security (RLS) habilitado em **todas** as tabelas do schema `public`.

## Diagrama de relacionamento (visão simplificada)

   │                            │                         ├── avaliacoes_clientes (prestador avalia cliente)

## Tabelas por domínio

### Identidade e perfil

| Tabela | Propósito |
|---|---|
| `prestadores` | Perfil de prestador de serviço — dados profissionais, status, ativação |
| `perfis` | Legado — 0 linhas, não referenciado em nenhum fluxo de código ativo |
| `profiles` | Dados complementares de perfil, incluindo `role` (`novo`/`cliente`/`prestador`) — tabela ativa |
| `perfis_admin` | Controle de acesso administrativo (`owner`, `moderator`, `editor`) |

**Ação recomendada:** `perfis` continua com 0 linhas — mantida como candidata a remoção, como já indicado anteriormente.

### `prestadores`

Tabela central do domínio profissional. Schema real (colunas relevantes):

```sql
id bigint generated by default as identity   -- PK, número
created_at timestamptz
nome text, bio text, whatsapp text
user_id uuid                                  -- FK auth.users
cliques_whatsapp integer default 0
foto_perfil text
bairro text
status text default 'pendente'                -- 'pendente' | 'ativo' | outros
aprovado_em timestamptz
bloqueado boolean default false
motivo_bloqueio text
habilidades text[], tags text[]
estado_sigla text default 'PR'
cidade_id uuid, regiao_id uuid                 -- FK cidades/regioes
slug text unique
cidades_atendidas text[]
origem_tipo text default 'registro_direto'     -- ver valores abaixo
verificado boolean default false
grupo_id uuid, categoria_id uuid               -- FK categorias_grupos/categorias
ativacao_status text not null default 'nao_enviado'  -- CHECK constraint, 7 valores (ver abaixo)
ativacao_enviado_em, ativacao_respondeu_em timestamptz
ativacao_obs text
garantia_dias smallint default 0               -- CHECK: apenas 0, 30, 60 ou 90
portfolio_obrigatorio boolean default true
sessao_fotos_titulo text
sessao_fotos_urls text[]                       -- CHECK: no máximo 5 URLs
```

**Índices/constraints confirmados:** `slug` (unique), `ativacao_status` (CHECK), `garantia_dias` (CHECK).

**`status`** — controla se o prestador aparece publicamente e se é redirecionado para completar cadastro.

**`ativacao_status`** — funil de ativação via WhatsApp, CHECK constraint com 7 valores: `nao_enviado` → `enviado` → `respondeu_positivo`/`respondeu_negativo`/`sem_whatsapp` → `perfil_completo` → `avaliacao_recebida`.

**`origem_tipo`** — `registro_direto` (auto-cadastro), `curadoria_publica` (curadoria manual inicial), `reivindicado`, e `vitrine` (prioridade máxima na busca). Sem CHECK constraint nesta coluna — outros valores não são impedidos a nível de banco.

**`garantia_dias`** — garantia declarada pelo prestador (postura comercial), campo agora implementado e em produção. Alimenta o sistema de `solicitacoes_garantia` (ver seção própria abaixo). Independe da garantia legal do CDC (90 dias para serviços duráveis), que se aplica sempre.

**`portfolio_obrigatorio`** — quando `false`, trava a criação do projeto no fluxo `sem_fotos` (ver `portfolio_projetos.sem_fotos`).

**`sessao_fotos_titulo` / `sessao_fotos_urls`** — sessão de fotos pública personalizada do prestador, independente do portfólio de projetos.

**Nota de tipagem:** verificar se `user_id`, `garantia_dias`, `portfolio_obrigatorio` e os campos de `sessao_fotos_*` já estão declarados em `types/prestador.ts` (`Prestador`/`PrestadorFormData`) — no levantamento anterior `user_id` não estava.

**Nota sobre design em avaliação anterior:** a proposta de substituir `bairro` por coordenadas (`latitude`/`longitude` + `endereco_texto` + `raio_atuacao_km`) e adicionar campos de "vitrine paga" (`vitrine_lance_atual`/`vitrine_pago_ate`) **não está implementada no schema atual** — nenhum desses campos existe em `prestadores`. Segue como roadmap.

| `categorias` | Categoria específica de serviço, vinculada a um grupo, flag `destaque` |

### Portfólio e execução de serviço

| Tabela | Propósito |
|---|---|
| `portfolio_projetos` | Um projeto/serviço contratado — status, cliente (`cliente_whatsapp` e âncora forte `cliente_user_id`), token de avaliação |
| `portfolio_fotos` | Fotos de um projeto, com legenda e comentário do cliente |
| `portfolio_comentarios` | Comentários no projeto, de cliente ou prestador (`autor_tipo`) |
| `portfolio_curtidas` | Curtidas de usuários autenticados em projetos (portfólio público) |
| `projeto_logs` | Log de ações realizadas em um projeto (auditoria) |
| `orcamentos` | Orçamento formal emitido pelo prestador ao cliente — **mencionado aqui, mas sem implementação ativa confirmada no frontend** |

**`portfolio_projetos.status`** — valores reais em uso: `em_registro` → `pendente` → `em_execucao` → `finalizado`. O valor `em_andamento` não é válido — nunca é gravado no banco.

**`cliente_user_id` vs `cliente_whatsapp`:** vínculo do cliente ao projeto migrado de âncora fraca (`cliente_whatsapp`) para âncora forte (`cliente_user_id` uuid, FK `auth.users`). O WhatsApp é mantido apenas como dado de contato legível. RLS já reflete essa migração — há policies específicas para "reivindicar" o projeto (`portfolio_projetos_reivindicar_cliente`) vinculando `cliente_user_id` a partir do WhatsApp do `profiles`.

**Novos campos confirmados no schema (não documentados anteriormente):**
- `sem_fotos` (boolean, default `false`) — travado na criação a partir de `prestadores.portfolio_obrigatorio = false`. Define se o projeto segue o fluxo sem etapas de foto (aceite → marcar concluído → avaliação).
- `marcado_concluido_at` (timestamptz) — preenchido quando o prestador marca como concluído no fluxo `sem_fotos`; libera o link de avaliação, equivalente ao papel da 3ª foto no fluxo com fotos.
- `aceito_at` (timestamptz) — momento em que o projeto foi aceito.
- `cliente_nome` (text).

**`avaliacao_token`** — UUID único por projeto (constraint `unique`), usado pelo cliente para acessar a página de avaliação/acompanhamento sem login. O design de exigir login (Google) desde o primeiro acesso **ainda não está implementado** — o token continua sendo o mecanismo de acesso público.

**`orcamentos`** — tabela existe no banco (0 linhas atualmente), com `numero_sequencial` (sequence própria), `itens` (jsonb), `layout_config` (jsonb com tema/cor), `status`, `validade`, `lido_em`, `aceito_em`. Estrutura pronta, mas **sem uso confirmado em produção** — mencionar como feature em construção/roadmap, não como ativa.

### Avaliação e confiança

| Tabela | Propósito |
|---|---|
| `avaliacoes` | Avaliação do cliente sobre o prestador, vinculada a um projeto |
| `avaliacoes_clientes` | Avaliação do prestador sobre o cliente — **avaliação bidirecional, já implementada e em uso** |
| `solicitacoes_garantia` | Casos de garantia/reclamação pós-serviço — substitui o antigo fluxo de `contestacoes` |
| `garantia_fotos` | Fotos anexadas à timeline de um caso de garantia |
| `garantia_comentarios` | Comentários por foto (ou gerais ao caso) na timeline de garantia |
| `contestacoes` | **Desativada** — 0 linhas, substituída pelo novo sistema de garantia |
| `denuncias` | Denúncia de um prestador (fora do contexto de avaliação) |

**`avaliacoes` — campos-chave:** `nota` (1–5, CHECK), `indica` (boolean), `visivel`, `status`, `em_disputa`, `resposta_prestador`, `cliente_nome`, `cliente_foto_url`.

**Novos campos em `avaliacoes` (ligados ao sistema de garantia):**
- `oculta_por_garantia` (boolean, default `false`) — quando `true`, a avaliação some da listagem pública do portfólio, mas permanece visível no detalhe do projeto. Nunca é deletada.
- `resolvido_via_garantia_id` (uuid) — referência ao caso de garantia que resolveu/alterou o resultado da avaliação.
- `nota_efetiva` (integer, nullable) — nota usada em médias/ranking. `NULL` = usar `avaliacoes.nota` normalmente. `avaliacoes.nota` **nunca** é sobrescrita; `nota_efetiva` preserva o dado original quando um caso de garantia altera o resultado (nota nova do cliente, nota 1 automática por sem-resposta, ou nota 3 neutra quando o prestador resolve reparo que ele mesmo ofereceu).

**`avaliacoes_clientes` (nova, avaliação bidirecional já ativa):**
```sql
id uuid, projeto_id uuid unique, prestador_id bigint,
cliente_user_id uuid, nota integer (1–5, CHECK),
motivos text[], created_at timestamptz
```
RLS implementa acesso por vínculo: o prestador pode consultar as avaliações de clientes associadas aos seus prestadores, e o cliente pode consultar a própria avaliação recebida. A migration atual não implementa janela de 14 dias nem liberação condicionada ao status `finalizado` da avaliação do prestador; esse comportamento não deve ser tratado como garantia de privacidade double-blind no banco.

**Sistema de garantia (`solicitacoes_garantia`) — em produção:**
```sql
id uuid, projeto_id uuid, prestador_id bigint, cliente_user_id uuid,
origem text ('cliente' | 'prestador'),
status text CHECK: 'aguardando_aceite_cliente' | 'aberta' | 'respondida' |
                    'sem_resposta' | 'resolvida' | 'recusada',
tipo text CHECK: 'garantia' | 'reclamacao',
prazo_resposta date,
descricao_problema text, fotos_problema text[],
resposta_prestador_garantia text, data_resposta timestamptz,
resolucao_descricao text, fotos_resolucao text[], data_resolucao timestamptz,
avaliacao_id uuid, nota_resultante integer (1–5, CHECK)
```

- **Fluxo de status:** `aguardando_aceite_cliente` → `aberta` → (`respondida` → `resolvida`) | `sem_resposta` | `recusada`.
- **`origem = 'cliente'`**: cliente relata problema dentro do prazo de garantia do prestador.
- **`origem = 'prestador'`**: prestador oferece reparo em reação a avaliação negativa; só vira caso ativo (`aberta`) após o cliente aceitar.
- **`tipo = 'garantia'`** (prestador tem `garantia_dias > 0`, prazo configurável) vs **`tipo = 'reclamacao'`** (prestador sem garantia formal, `garantia_dias = 0`, prazo fixo de 15 dias corridos após `finalizado`). Mesma máquina de estados; muda apenas elegibilidade e linguagem exibida.

**`garantia_fotos`** — sem posições fixas (diferente de `portfolio_fotos`), sequência livre. Campo `fase` (CHECK: `problema` | `resolucao`) marca se a foto documenta o problema ou a resolução — escolhido explicitamente por quem envia, não inferido pelo status do caso. Campo `publica` (boolean): quando `true`, a foto foi promovida do bucket privado para exibição pública (ex.: perfil do prestador); só fotos com `fase = resolucao` são elegíveis, promovidas quando o caso fecha como `resolvida`.

**`contestacoes` — desativada:** a tabela ainda existe no schema (0 linhas), mas foi **substituída** pelo fluxo de `solicitacoes_garantia`. Mantida por enquanto sem uso ativo; candidata a remoção futura junto com `perfis`.

## Row Level Security (RLS) — padrão observado

```sql
-- Padrão de policy de UPDATE/DELETE em tabelas vinculadas a prestador
EXISTS (
  SELECT 1 FROM portfolio_projetos
  JOIN prestadores ON prestadores.id = portfolio_projetos.prestador_id
  WHERE portfolio_projetos.id = <tabela>.projeto_id
    AND prestadores.user_id = auth.uid()
)
```

Cadeia de verificação: `auth.uid() → prestadores.user_id → prestadores.id → portfolio_projetos.prestador_id`.

**Novo padrão (garantia):** as tabelas `garantia_fotos` e `garantia_comentarios` usam tanto policies inline (join `solicitacoes_garantia` + `prestadores`) quanto uma função auxiliar `usuario_tem_acesso_ao_caso_garantia(caso_id)` — os dois padrões coexistem nas mesmas tabelas (indício de policies antigas e novas não totalmente consolidadas).

**Leitura pública:** fotos de portfólio têm policy `SELECT` com `qual: true` — visibilidade pública total. Fotos de garantia só são públicas quando `publica = true`.

**Ponto de atenção operacional:** como o RLS depende de `auth.uid()`, qualquer falha de sessão no client resulta em erro silencioso de permissão negada, não "não encontrado". Ao debugar update/insert que "não faz sentido", checar sessão antes de suspeitar de lógica de negócio.

**Ponto de atenção adicional:** várias tabelas (`prestadores`, `anuncios`, `cidades`, `estados`, `perfis`, `logs_atividades`) têm múltiplas policies com nomes diferentes cobrindo o mesmo `cmd` (ex.: 6+ policies de `SELECT` em `prestadores`) — sinal de policies acumuladas ao longo do tempo sem limpeza. Não afeta a funcionalidade (Postgres usa `OR` entre policies permissivas do mesmo tipo), mas dificulta a leitura e manutenção. Vale uma auditoria e consolidação futura.
